## Platform and application structure

Ship iOS and Android first. Keep the current web target for development previews and static-export checks; a production web experience is outside the first release. Preview builds use synthetic data and must not connect to production journals. Keep Expo Router, TypeScript, React's local state, and the current themed primitives. Add an auth context when authentication exists; do not introduce a global store, query-cache library, or repository framework preemptively.

Put actual integrations in focused modules under `src/services/` when their features are built. Keep SDK objects and transport errors out of screens, and keep domain/date rules independent of React and Firebase. Server code belongs in a separate `functions/` TypeScript package. These directories should be created with working implementations, not empty scaffolding.

## Firebase

Use the modular APIs of **React Native Firebase** for Auth, Firestore, Functions, and App Check in native development builds. Durable offline personal data is a mobile requirement: the Firebase JavaScript SDK does not support Firestore persistence in React Native, while the native SDK supports it. This justifies the native-build setup and means Expo Go will cease to be the primary runtime when integration begins. [Firebase environment support](https://firebase.google.com/docs/web/environments-js-sdk), [native Firestore persistence](https://rnfirebase.io/firestore/usage#offline-capabilities), [Expo integration](https://docs.expo.dev/guides/using-firebase/).

- Use separate development and production Firebase projects, local Auth/Firestore/Functions emulators for integration tests, Firestore Standard edition, and `us-central1` for the initial database and functions. This is a US-first infrastructure default; provision it deliberately because database location is a durable choice.
- Use email/password accounts with verified cloud personal-data writes, enforcing verification and ownership at Firestore rules and privileged handlers. Sign-up creates Auth identity; defer personal application records until verification. The [verification gate](../APP_NAVIGATION_AND_UX.md#106-verify-email--planned--v1) immediately follows sign-up and precedes onboarding, including restored unverified sessions. Refresh SDK verification/token authorization state before verified writes; a client flag or route guard is not authorization. Password reset and account deletion are V1. No guest/local-only, anonymous, or social auth. Bundled authored content is static/read-only at the data boundary; its storage does not introduce public screens or bypass account/verification/onboarding gates.
- Keep user settings at `users/{uid}`, journeys at `users/{uid}/journeys/{journeyId}`, daily records under each journey's `days/{dayNumber}`, and journal entries separately at `users/{uid}/journalEntries/{entryId}`. Store references between records rather than large growing arrays on the user document. Pin each journey to an immutable published local content version under the [content specification](../FORMATION_CONTENT_SPEC.md#v1-storage-and-versioning). These paths do not add a standalone journal UI or per-practice note feature to V1.
- Apply the ownership, field protection, and handler authorization requirements in `AGENTS.md` with emulator tests alongside each collection's implementation. Application-authored formation content is read-only to clients. See official [security rules](https://firebase.google.com/docs/firestore/security/get-started), [field access](https://firebase.google.com/docs/firestore/security/rules-fields), and [query constraints](https://firebase.google.com/docs/firestore/security/rules-query).
- Use the native persistence/account boundary below for offline personal records and sync. Merge independent practice fields rather than overwriting whole days. Preserve concurrent journal-like text edits as revisions instead of silently choosing one version of prose. Firestore otherwise resolves competing document writes with last-write-wins behavior. [Offline behavior](https://firebase.google.com/docs/firestore/manage-data/enable-offline).
- Reflections, journals, intentions, and personal prayer content are private by default. V1 has no public sharing, community feed, or public profile; future membership never implies item-specific sharing consent. Account deletion must remove Firebase Auth identity and nested personal application records through an authenticated backend operation. Authorize that handler independently of rules, handle partial failure/retry, and complete the local private-data boundary before declaring deletion/sign-out successful. Do not promise exact backup-erasure timing without verified provider/infrastructure policy.
- Use second-generation callable Functions with TypeScript and Node 22 for privileged operations. This is the separate `functions/` package's runtime; the app/tooling package uses Node 24. Recheck Firebase's [supported runtimes](https://firebase.google.com/docs/functions/manage-functions#set_nodejs_version) during implementation. Verify Auth and enforce native App Check for production requests; use only development debug providers in local testing. Store third-party secrets in Secret Manager through Firebase secret parameters. [Callable Functions](https://firebase.google.com/docs/functions/callable), [secret configuration](https://firebase.google.com/docs/functions/config-env).

The [commercial policy](../PRODUCT_REQUIREMENTS.md#identity-mission-and-commercial-principles) keeps participation free. Hosting services can still incur costs: production provisioning must include billing budgets/alerts, bounded function instances, and request quotas. No cloud project, billing configuration, or deployment is created by this decision record.

## Offline persistence and account boundaries

**Planned — V1, not implemented/tested.** After relevant journey data has loaded, completion toggles, intentions, and reflection drafts must work offline through native Firestore persistence. Local authored content is available offline by pinned version; legally usable bundled Scripture remains separate and is readable without a network request once supplied. Any later remote-only translation follows its verified storage terms. Login, sign-up, verification, password reset, account deletion, and initial journey creation require connectivity. Existing verified sessions may use loaded private records offline under the actual SDK session semantics.

Expose local saved/pending-sync, server-confirmed saved, and failed/rejected outcomes accurately when material. Keep draft persistence separate from completion and avoid whole-record replacement that drops independent edits. Do not describe cached journals as end-to-end encrypted or copy them into general-purpose unencrypted storage or diagnostics.

The [Account sign-out contract](../APP_NAVIGATION_AND_UX.md#1022-account) settles participant behavior: attempt sync if online; if writes remain, offer cancel-and-keep or explicitly confirmed discard-and-sign-out. Direct multi-account switching is excluded from V1. Technical implementation must stop prior-account listeners, clear private in-memory/navigation state, and isolate/remove prior-account cached private records and pending mutations before another sign-in. Auth sign-out alone is not evidence that the Firestore cache has been cleared. Confirmed discard must also prevent discarded mutations from later syncing; it must not delete already-synced remote records.

Verify supported native SDK persistence/lifecycle APIs during integration rather than guessing a cache-clearing sequence. Test online sync, offline pending writes, cancellation, confirmed discard, sync/cleanup failure, relaunch, and signing into a different synthetic account. If the cache boundary cannot be completed, keep another account's sign-in blocked behind recovery; do not report a successful safe transition. These are required implementation boundaries, not claims that the chosen SDK already provides the full flow.

## Local reminders and diagnostics

V1 reminders use local-device scheduling only; no backend push infrastructure. Device-local scheduling and the fixed journey timezone serve different purposes; [Notification Settings](../APP_NAVIGATION_AND_UX.md#1020-notification-settings--planned--v1) owns enablement, chosen time, permission, and error flows. Introduce only the required native integration when this feature is scoped, verifying its installed Expo SDK APIs. No notification integration exists today.

V1 uses no behavioral product analytics, advertising integration, or marketing/ad identifiers. Firebase Crashlytics is permitted for crash diagnostics only with private content excluded from logs, breadcrumbs, custom keys, and payloads. It is not installed or configured. Apply the [product privacy/data rules](../PRODUCT_REQUIREMENTS.md#privacy-telemetry-and-data-lifecycle) across services, caches, URLs, notification payloads, and support diagnostics. Help/Feedback opens configured support contact; no Firebase support-ticket system or V1 marketing/newsletter/devotional-email backend.

## Curated Scripture

**Selected by the product owner on 2026-09-07; data boundary and validation implemented, production content and journey-backed UI pending.** Scripture uses a fixed curated 77-day reading plan. It has no third-party Bible API, credentials, gateway, catalog discovery, or arbitrary-passage requests. V1 favors bundled structured content for permitted translations; static Scripture does not require Firestore reads.

The content lives under [`src/content/scripture/`](../../src/content/scripture/reading-plans.ts):

- `reading-plans.ts` holds the settled weekly themes and versioned day → theme/passage assignments. The current `v1-draft` has no approved assignments and is never exposed as a published plan. Published versions retain approval evidence and remain immutable for pinned historical journeys.
- `passages.ts` holds canonical passage IDs, book IDs, display references, and ordered per-chapter inclusive verse ranges. A passage may cross chapters within one book; explicit adjacent ranges avoid a general-purpose reference parser. Referenced books carry verified chapter verse counts and source evidence for range validation and complete-book audits. No book metadata or references have been invented.
- `translations.ts` is the only translation registry and fallback configuration. IDs such as `nasb2020` and `nasb1995` distinguish editions independently of storage. Metadata records availability, licensing evidence or a TODO, verified attribution (null only when verified as unnecessary), and content source/revision when supplied.
- `texts.ts` stores only required passage/translation records with ordered verse coordinates and unmodified verified text. All text arrays are currently empty. No full Bible is bundled.

[`src/services/scripture.ts`](../../src/services/scripture.ts) owns day resolution, available reader metadata, preference resolution, and `loadScriptureText(contentVersion, passageId, translationId)`. Screens must use this boundary, never import content files or select their own translations. The loader already returns a Promise so a future translation-specific remote source can be added there without changing the reader contract; no remote adapter or speculative backend exists. A local Promise does not justify a network spinner or artificial delay. Keep known references visible and show loading/retry only for a real pending/retryable operation.

Store the user's eventual preference as `TranslationId`, alongside other private user settings. The inspected scaffold had no saved preference, user records, storage keys, or external version IDs to migrate, so no compatibility mapping or persistence layer was added. `resolveTranslationPreference` accepts unknown stored input, uses an available exact ID or the configured available BSB fallback, and returns the actual reader label plus whether fallback was used. The strict text loader never substitutes translations. Selection never changes passage identity, content version, or completion.

Only a cleared, enabled translation with complete supplied text for the published plan appears in selection results. Development validation also requires each enabled translation to cover every retained published plan. If no usable fallback exists, return unavailable and preserve known references and unrelated practices. The existing route screens remain truthful navigation scaffolds until real auth/journey state, saved settings, and approved content are connected; do not expose published future-day readings through the current public scaffold.

All 14 target translations are registered but disabled. The [BSB publisher terms](https://berean.bible/terms.htm), checked 2026-09-07, dedicate the text to the public domain and make attribution optional. BSB is the configured fallback candidate, with `attribution: null`; no source text has yet been imported or verified. KJV remains pending exact source, attribution, and territory review; Cambridge documents [UK administration of KJV rights](https://assets.cambridge.org/97805211/63347/copyright/9780521163347_copyright_info.pdf). Every other target remains pending permission, exact notices, and content. An unavailable translation's TODO is internal configuration, never reader attribution. Before importing any text, verify the actual source edition and intended redistribution, record provenance/revision, and preserve the approved wording. Do not scrape Bible sites/APIs or obtain uncleared datasets.

A translation requiring remote distribution later needs verified terms, source ownership, response validation, and failure/offline behavior implemented behind the existing boundary. Do not assume remote storage itself grants permission. Do not persist translation text into personal records, journals, logs, or diagnostics, and never label one translation's text as another. Translation-specific omissions/numbering must be reviewed against canonical coordinates before enabling content; structural validation cannot establish textual authenticity or permission.

[`src/scripture/validation.ts`](../../src/scripture/validation.ts) and the [testing guide](testing.md) define structural checks and the reproducible verse audit. Human curriculum approval and source/legal verification remain separate release requirements under the [content specification](../FORMATION_CONTENT_SPEC.md#production-approval-and-publication).

## Journey data and content ownership

Read [the navigation and UX contract](../APP_NAVIGATION_AND_UX.md) for settled start/progression, completion, preference timing, history/future-day access, and ended-journey behavior. [Product requirements](../PRODUCT_REQUIREMENTS.md) owns initial V1 exclusions and future repeat-journey scope; this record does not maintain a second journey-flow specification.

Keep domain/date calculations independent of UI and transport. Persist the journey's start calendar date and fixed IANA timezone captured at creation, effective-dated/snapshotted practice configuration for each day (including days with no edits yet), pinned content version, and represented practice date separately from the edit timestamp. Enforce one active journey and idempotent initial creation at the appropriate data boundary. These records must support the contract's history and correction behavior without overwriting earlier journeys. Draft persistence is separate from an explicit practice-completion action. Exact schema and concurrent-write validation belong with the affected feature. Future variant plans must preserve per-journey historical content and shared group assignments under the content specification; do not implement selectors or Community infrastructure for V1.
