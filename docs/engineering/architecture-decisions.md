## Platform and application structure

Ship iOS and Android first. Keep the current web target for development previews and static-export checks; a production web experience is outside the first release. Preview builds use synthetic data and must not connect to production journals. Keep Expo Router, TypeScript, React's local state, and the current themed primitives. Add an auth context when authentication exists; do not introduce a global store, query-cache library, or repository framework preemptively.

Put actual integrations in focused modules under `src/services/` when their features are built. Keep SDK objects and transport errors out of screens, and keep domain/date rules independent of React and backend SDKs. Amplify Gen 2 backend definitions belong under `amplify/`; needed Lambda definitions/handlers belong under `amplify/functions/`. Create these with working scoped implementations, not empty scaffolding.

## AWS Amplify Gen 2

Use **AWS Amplify Gen 2** as the backend development and deployment framework for the Expo / React Native / TypeScript application. Amplify defines the required AWS resources in TypeScript. The intended service boundaries are:

| Capability                      | Application interface                       | Underlying AWS service / scope                              |
| ------------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| Authentication                  | Amplify Auth                                | Amazon Cognito, **Lite** feature plan                       |
| Application data                | Amplify Data                                | AWS AppSync GraphQL API and Amazon DynamoDB                 |
| File/object storage             | Amplify Storage                             | Amazon S3, only for a concrete file-storage requirement     |
| Trusted business logic          | Amplify-defined functions/custom operations | AWS Lambda, only where trusted server execution is required |
| Future real-time community data | Amplify Data real-time capabilities         | AWS AppSync subscriptions; no V1 Community implementation   |

Use the modular `aws-amplify` client APIs and required React Native integration packages when implementation begins; no backend packages are needed by today's scaffold. The [React Native quickstart](https://docs.amplify.aws/react-native/start/quickstart/) requires native modules unavailable in Expo Go. Use Expo development builds for the integration and retain EAS for mobile builds/distribution. Verify compatibility against the exact Expo SDK 57 and installed Amplify versions before installing native peers; do not copy a tutorial's older Expo dependencies or add Amplify UI just for authentication. AWS currently marks React Native Web support as unofficial; preserve a separate synthetic web preview without importing native-only modules into its bundle.

### Authentication and identity

Use email/password sign-up, sign-in, sign-out, session restoration, email verification, email-only password recovery, and account deletion. Explicitly configure **Cognito Lite** unless a documented settled requirement needs an Essentials feature. Do not accept a console or infrastructure default of Essentials: set the user pool's `UserPoolTier` to `LITE` in backend code, using the Amplify-exposed CDK resource when needed, and verify the synthesized and deployed setting. Use the Lite-compatible password/SRP flow; do not opt into choice-based `USER_AUTH`, managed login, passkeys, SMS authentication/MFA, email MFA, or token customization without a product need. Email confirmation and recovery codes are not passwordless sign-in or MFA. [Cognito feature plans](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-sign-in-feature-plans.html), [user-pool tier property](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cognito-userpool.html#cfn-cognito-userpool-userpooltier), [Amplify Auth CDK customization](https://docs.amplify.aws/react-native/build-a-backend/auth/modify-resources-with-cdk/).

Require email confirmation before Cognito issues an authenticated session; do not auto-confirm unverified accounts. Sign-up creates only the identity until verification and sign-in complete. Use email confirmation codes and handle Amplify Auth's confirmation and session next steps at the existing [Verify Email gate](../APP_NAVIGATION_AND_UX.md#106-verify-email--planned--v1); an unconfirmed account is not a signed-in session. Existing authenticated-but-unverified sessions must also pass that gate. Defer application records until verified; refresh session authorization state when necessary. Password recovery must complete the email-code/new-password step before reporting success. No guest/local-only, anonymous, or social auth. [Sign-up confirmation](https://docs.amplify.aws/react-native/frontend/auth/sign-up/), [password recovery](https://docs.amplify.aws/react-native/build-a-backend/auth/manage-users/manage-passwords/).

Use an authenticated user ID in domain types, mapped at the service boundary to the Cognito user pool's immutable `sub`, not email or a client-supplied owner. Amplify's generated owner representation must be handled at that boundary; do not assume it is identical to a domain `userId` field. Owner authorization does not itself test `email_verified`. Verify the Cognito confirmation configuration and deny unverified cloud writes at the backend; if a supported path can issue an unverified session, enforce verification in the affected server-side operations without leaving generated mutations as a bypass. A route guard or local verification flag is never authorization.

### Application data and authorization

Define domain models in `amplify/data/resource.ts` and access them through the typed Amplify Data client behind focused services. AppSync and DynamoDB are the underlying services; mobile clients do not query physical DynamoDB tables. Preserve these conceptual records, with Amplify provisioning their underlying resources:

| Model          | Responsibility / relationships                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `UserProfile`  | Private onboarding state and settings/preferences for one authenticated user; no additional public profile fields                                            |
| `Journey`      | Owner, start date, fixed timezone, pinned content version, and effective-dated practice selections                                                           |
| `DailyEntry`   | Journey ID and day number, that day's applicable practices, explicit completion states, and private intention/reflection drafts or their revision references |
| `JournalEntry` | Separate owner/journey-related private writing when scoped; does not add a standalone journal UI or per-practice notes to V1                                 |

Use model IDs and relationship fields, bounded owner/journey/day queries, pagination, and indexes driven by actual access patterns. Do not grow arrays of all days or journals on a profile. Progress may be derived from day records; avoid a separately synchronized aggregate without a current need. Each private related model needs its own authorization; a relationship does not inherit its parent's ownership or guarantee cascade deletion. Pin journeys to immutable published local content under the [content specification](../FORMATION_CONTENT_SPEC.md#v1-storage-and-versioning). Bundled authored content remains read-only and requires no application-data reads; its storage does not bypass account/verification/onboarding gates. [Data modeling](https://docs.amplify.aws/react-native/build-a-backend/data/data-modeling/).

Use Cognito user-pool authorization and per-owner Amplify Data rules for private records. Broad authenticated access grants access to other signed-in users and is not a substitute for ownership. Multiple allow rules combine with OR; protect ownership fields from reassignment, constrain mutable/protected fields, and validate cross-record ownership and domain invariants at the server boundary. Use model/field rules and supported validation first, then a custom AppSync operation or Lambda only for a requirement they cannot enforce. Apply these constraints to every reachable mutation, including generated operations. IAM limits deployment and service-role access; it does not replace participant authorization. Test allowed and denied operations against an isolated AWS backend alongside each model's implementation. [Authorization rules](https://docs.amplify.aws/react-native/build-a-backend/data/customize-authz/), [owner-field protection](https://docs.amplify.aws/react-native/build-a-backend/data/customize-authz/per-user-per-owner-data-access/).

Reflections, journals, intentions, personal prayer content, journey records, and settings remain private by default. Keep future explicitly shared items separate from private records, even where field-level authorization is available. Future Community may use membership/role authorization and scoped AppSync subscriptions for prayer requests, encouragement, group updates, and shared activity; membership never implies consent to share personal content. Do not create these models, subscriptions, or entry points in V1. [Amplify Data subscriptions](https://docs.amplify.aws/react-native/frontend/data/subscribe-data/).

### Trusted operations, storage, and secrets

Use AWS Lambda through Amplify when trusted coordination is necessary. Account deletion is such a V1 operation: authenticate the requester, derive the target identity from trusted claims, remove all related private application records, and then remove the Cognito identity. Authorize the handler independently and give its IAM role only required access. Handle paginated deletion, partial failure, retry/idempotency, and concurrent or queued writes so deleted records cannot be recreated. Complete the local private-data boundary before reporting success; deleting only the identity is insufficient. Do not promise exact backup-erasure timing without verified infrastructure policy. Prefer standard Amplify Data capabilities for routine reads/writes instead of invoking a function for every action. Select a runtime supported by the installed Amplify tooling and AWS Lambda when a function is implemented; the app/tooling package remains Node 24. [Amplify functions](https://docs.amplify.aws/react-native/build-a-backend/functions/set-up-function/).

Add Amplify Storage backed by Amazon S3 only when a scoped feature needs files/objects. Current personal text records and bundled formation/Scripture content do not require a bucket. Any later remote Scripture source still needs verified distribution terms and the existing service boundary. Define Storage access separately from Data authorization, using scoped identity/IAM permissions and explicit sharing controls. [Amplify Storage](https://docs.amplify.aws/react-native/build-a-backend/storage/).

Never bundle static AWS access keys, deployment credentials, or backend secrets into Expo, `EXPO_PUBLIC_*`, or client outputs. Cognito/Amplify manage authenticated application access; IAM roles authorize backend services. Use Amplify's backend secret configuration and `secret()` references for needed secret values, scoped to the appropriate sandbox or deployed environment. Do not commit secrets or include them in diagnostics. [Backend secrets](https://docs.amplify.aws/react-native/build-a-backend/functions/environment-variables-and-secrets/).

## Offline persistence and account boundaries

**Planned — V1, not implemented/tested.** After relevant journey data has loaded, completion toggles, intentions, and reflection drafts must work offline through a durable, account-scoped local store and pending-mutation queue that synchronize through Amplify Data. Gen 2 does not provide DataStore support; the Data client and `observeQuery` must not be treated as a durable offline database or write queue. Select and verify a native persistence mechanism, private-data protection, retry policy, and synchronization lifecycle with the first personal-data feature; none is installed today. This is a V1 delivery requirement, not a reason to add speculative infrastructure here. [Gen 2 capability matrix](https://docs.amplify.aws/react-native/start/migrate-to-gen2/feature-matrix/).

Local authored content is available offline by pinned version; legally usable bundled Scripture remains separate and is readable without a network request once supplied. Any later remote-only translation follows its verified storage terms. Login, sign-up, verification, password reset, account deletion, and initial journey creation require connectivity. Existing verified sessions may use loaded private records offline under the actual SDK session semantics; queued writes must recheck authorization when reconnecting.

Expose local saved/pending-sync, server-confirmed saved, and failed/rejected outcomes accurately when material. Keep draft persistence separate from completion. Merge independent practice fields rather than replacing whole days, and preserve concurrent journal-like text edits as revisions instead of silently choosing one version of prose. Define idempotency and conflict checks at the service/backend boundary; subscriptions alone do not resolve concurrent writes. Do not describe cached journals as end-to-end encrypted or copy them into general-purpose unencrypted storage or diagnostics.

The [Account sign-out contract](../APP_NAVIGATION_AND_UX.md#1022-account) settles participant behavior: attempt sync if online; if writes remain, offer cancel-and-keep or explicitly confirmed discard-and-sign-out. Direct multi-account switching is excluded from V1. Technical implementation must stop prior-account subscriptions and sync workers, clear private in-memory/navigation state, and isolate/remove prior-account cached private records and pending mutations before another sign-in. Amplify Auth sign-out alone does not clear an application-owned cache or queue. Confirmed discard must also prevent discarded mutations from later syncing; it must not delete already-synced remote records.

Verify the selected native store and Amplify session/lifecycle APIs during integration rather than guessing a cache-clearing sequence. Test online sync, offline pending writes, cancellation, confirmed discard, sync/cleanup failure, relaunch, and signing into a different synthetic account. If the cache boundary cannot be completed, keep another account's sign-in blocked behind recovery; do not report a successful safe transition. These are required implementation boundaries, not claims that the chosen SDK already provides the full flow.

## Curated Scripture

**Selected by the product owner on 2026-09-07; data boundary and validation implemented, production content and journey-backed UI pending.** Scripture uses a fixed curated 77-day reading plan. It has no third-party Bible API, credentials, gateway, catalog discovery, or arbitrary-passage requests. V1 favors bundled structured content for permitted translations; static Scripture does not require Amplify Data reads or S3 storage.

The content lives under [`src/content/scripture/`](../../src/content/scripture/reading-plans.ts):

- `reading-plans.ts` holds the settled weekly themes and versioned day → theme/passage assignments. The current `v1-draft` has no approved assignments and is never exposed as a published plan. Published versions retain approval evidence and remain immutable for pinned historical journeys.
- `passages.ts` holds canonical passage IDs, book IDs, display references, and ordered per-chapter inclusive verse ranges. A passage may cross chapters within one book; explicit adjacent ranges avoid a general-purpose reference parser. Referenced books carry verified chapter verse counts and source evidence for range validation and complete-book audits. No book metadata or references have been invented.
- `translations.ts` is the only translation registry and fallback configuration. IDs such as `nasb2020` and `nasb1995` distinguish editions independently of storage. Metadata records availability, licensing evidence or a TODO, verified attribution (null only when verified as unnecessary), and content source/revision when supplied.
- `texts.ts` stores only required passage/translation records with ordered verse coordinates and unmodified verified text. All text arrays are currently empty. No full Bible is bundled.

[`src/services/scripture.ts`](../../src/services/scripture.ts) owns day resolution, available reader metadata, preference resolution, and `loadScriptureText(contentVersion, passageId, translationId)`. Screens must use this boundary, never import content files or select their own translations. The loader already returns a Promise so a future translation-specific remote source can be added there without changing the reader contract; no remote adapter or speculative backend exists. A local Promise does not justify a network spinner or artificial delay. Keep known references visible and show loading/retry only for a real pending/retryable operation.

Store the user's eventual preference as `TranslationId`, alongside other private user settings. The inspected scaffold had no saved preference, user records, storage keys, or external version IDs to migrate, so no compatibility mapping or persistence layer was added. `resolveTranslationPreference` accepts unknown stored input, uses an available exact ID or the configured available BSB fallback, and returns the actual reader label plus whether fallback was used. The strict text loader never substitutes translations. Selection never changes passage identity, content version, or completion.

Only a cleared, enabled translation with complete supplied text for the published plan appears in selection results. Development validation also requires each enabled translation to cover every retained published plan. If no usable fallback exists, return unavailable and preserve known references and unrelated practices. The existing route screens remain truthful navigation scaffolds until real auth/journey state, saved settings, and approved content are connected; do not expose published future-day readings through the current public scaffold.

All 14 target translations are registered but disabled. The [BSB publisher terms](https://berean.bible/terms.htm), checked 2026-09-07, dedicate the text to the public domain and make attribution optional. BSB is the configured fallback candidate, with `attribution: null`; no source text has yet been imported or verified. KJV remains pending exact source, attribution, and territory review; Cambridge documents [UK administration of KJV rights](https://assets.cambridge.org/97805211/63347/copyright/9780521163347_copyright_info.pdf). Every other target remains pending permission, exact notices, and content. An unavailable translation's TODO is internal configuration, never reader attribution. Before importing any text, verify the actual source edition and intended redistribution, record provenance/revision, and preserve the approved wording. Do not scrape Bible sites/APIs or obtain uncleared datasets.

A translation requiring remote distribution later needs verified terms, source ownership, response validation, and failure/offline behavior implemented behind the existing boundary. Do not assume remote storage itself grants permission. Do not persist translation text into personal records, journals, logs, or diagnostics, and never label one translation's text as another. Translation-specific omissions/numbering must be reviewed against canonical coordinates before enabling content; structural validation cannot establish textual authenticity or permission.

[`src/scripture/validation.ts`](../../src/scripture/validation.ts) and the [testing guide](testing.md) define structural checks and the reproducible verse audit. Human curriculum approval and source/legal verification remain separate release requirements under the [content specification](../FORMATION_CONTENT_SPEC.md#production-approval-and-publication).
