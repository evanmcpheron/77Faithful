# Testing and verification

Updated 2026-09-08. The repository has an operational lint/format/type/test setup and a small regression suite. Navigation-scaffold tests now exercise parser and route relationships; integrated product/backend tests are still future work.

## Tooling and conventions

- Node 24 and npm 11; `.nvmrc` and package engines define the supported development runtime. Use `npm ci` and commit lockfile changes with dependency changes.
- ESLint uses `eslint-config-expo/flat` plus `eslint-config-prettier`, which disables conflicting formatting rules. Prettier runs separately. Explicit `any`, incorrect type imports, and lint warnings fail verification.
- Jest 29 uses `jest-expo ~57.0.5` and the React Native 0.86.3 preset. React Native Testing Library 14 uses its `test-renderer` peer. Await `render`, `renderHook`, `act`, and user interactions; prefer accessible role/name queries and behavioral assertions.
- Tests are colocated as `src/**/*.test.tsx` or `*.test.ts`, outside `src/app/`. There are no snapshots or arbitrary coverage thresholds. Coverage collection includes untested source rather than just imported modules.
- `jest.setup.js` uses the official Worklets mock before Reanimated's test setup, and mocks the global CSS import. Keep real components/hooks under test; isolate native/platform or external-service boundaries. [Worklets setup](https://docs.swmansion.com/react-native-worklets/docs/guides/testing/), [Reanimated setup](https://docs.swmansion.com/react-native-reanimated/docs/guides/testing/).
- Jest disables Watchman for portable local/CI runs. Mock call history and spies are reset between tests; configure individual mock return values in each suite.

ESLint 9 is currently required by the peer range of `eslint-plugin-react` used by Expo's SDK 57 configuration. npm marks this ESLint major unsupported. Keep this constraint visible and move to a supported major when the Expo/plugin combination supports it; do not force incompatible peer dependencies. Jest 29 likewise follows this version of `jest-expo` rather than an independent latest-major upgrade.

## Check scope

For Markdown-only work, run `npm run format:check`, resolve relative links and any heading fragments in changed documents, and check new or changed external references with available tools. Use `git diff --check` for whitespace; it does not validate links or include untracked files. Format only affected files with the installed Prettier CLI rather than applying unrelated repository-wide fixes. No additional link-checking package is required. Report external references that could not be verified.

For reviews, follow the non-editing rules in [AGENTS.md](../../AGENTS.md). Use check commands rather than `format` or `lint:fix`. The type generation behind `typecheck` and `check` invokes Expo customization, which can update `tsconfig.json` if setup is incomplete; inspect configuration before using it in a review. Ignored type/build outputs are acceptable, but rewriting source/configuration is not part of a review.

Root Jest currently discovers only `src/**/*.test.[jt]s?(x)`. `npm run check` separately type-checks and synthesizes the current Auth-only `amplify/` definition, but it does not establish deployed Cognito behavior, future Data authorization, or Lambda handlers. Add local handler/service tests with those implementations, plus integration tests against an isolated Amplify cloud sandbox or dedicated AWS test backend. A sandbox provisions real AWS resources; it is not a local emulator. Use synthetic accounts/data, scoped test credentials, and documented setup/cleanup. Include credentialed integration checks in CI only when configured; do not invent an AWS emulation stack or provision infrastructure for unrelated work. Mocked or synthesized checks cannot establish AppSync authorization, Cognito email delivery, or native offline behavior.

## Curated Scripture validation

`npm run scripture:audit` runs the typed catalog validator and prints counts using [Node 24's built-in TypeScript stripping](https://nodejs.org/download/release/v24.10.0/docs/api/typescript.html#type-stripping). Data/validation modules used by this tool have type-only imports; the app service composes the same content for runtime use. No additional dependency or credential is needed. The command is part of `npm run check` and therefore CI. `npm run scripture:audit -- --release` additionally requires a complete published plan and enabled fallback; it intentionally fails for the current empty draft. Development checks passing do not establish content readiness.

`src/scripture/validation.test.ts` exercises duplicate/invalid days and IDs, weekly membership, missing approval, unknown references, missing enabled coverage across retained versions, malformed/ordered chapter ranges and text, source/rights requirements, and overlapping verse consistency. `src/scripture/content.test.ts` validates checked-in content, target registry/theme order, and honest unpublished/unavailable behavior. `src/services/scripture.test.ts` exercises daily resolution, stable preferences, unavailable choices, configured fallback and actual labels, strict text lookup/attribution, missing pinned versions, and no network use. All populated fixtures are explicitly synthetic non-Scripture data under `src/scripture/__fixtures__/`, never imported by production code.

The audit deduplicates canonical book/chapter/verse coordinates, including repeated and overlapping passages. Whole-book detection requires sourced chapter counts for each included book. Invalid catalogs fail instead of producing authoritative totals. Incomplete/unpublished plans return null final verse/book counts. Human approval, exact reference/text authenticity, and source/distribution permissions still require review; no schema/test substitutes for those checks. Current/historical/future gates, settings persistence, native reading accessibility, and completion remain unimplemented scaffold behavior.
