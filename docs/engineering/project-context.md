## Observed: source conventions and styling

TypeScript extends `expo/tsconfig.base` with `strict: true` and explicit `expo/types`, Jest, and Node ambient types. The installed base uses bundler module resolution, React JSX, `noEmit`, and `skipLibCheck`. Includes cover TypeScript source, `.expo/types/**/*.ts`, and `expo-env.d.ts`. `npm run typecheck` uses Expo's supported `customize tsconfig.json` command to regenerate route types before compilation; no running server is needed.

`@/*` resolves to `src/*`; `@/assets/*` resolves to root `assets/*`. Shared imports usually use aliases, with relative imports for siblings and the CSS module. Static images use literal `require(...)` calls. Source files use kebab-case; components/types use PascalCase and hooks/functions use camelCase. Routes/layout and `AppTabs` have default exports; shared components and hooks generally have named exports. Props typically use small type aliases composed with React Native props. There are no barrel files.

Prettier enforces two-space indentation, single-quoted JavaScript/TypeScript strings, semicolons, trailing commas, a 100-column print width, and same-line closing JSX brackets. ESLint checks the whole repository, uses Expo's rules, requires type-only imports where appropriate, and rejects explicit `any` and warnings.

Most styles are colocated `StyleSheet.create` objects with arrays for theme/platform/pressed values. `ThemedText`, `ThemedView`, `useTheme`, and theme constants provide a partial shared visual system. Web also uses CSS variables and a CSS module for the web switch adapter. See [design-system.md](design-system.md) for exact values and limitations.

## Observed: state, data, backend, and environment

The pure Journey domain in [`src/journey/`](../../src/journey/invariants.ts) now owns day/week invariants, validated date-only values and explicit IANA timezones, calendar progression, day access decisions, effective-dated optional practices and immutable daily definitions, participation status/full/partial counts, the approved current-run complete-day streak, and detection of multiple active Journeys. Navigation, Scripture, and the trusted Data handler reuse its rules; progress components reuse its count type. These modules have no React, AWS, persistence, network, or device-timezone dependency. The Data handler now enforces concurrent/idempotent Journey and DailyEntry creation, while route protection, Settings, and state-backed Today/history screens remain deferred.

The owner settled the streak definition in [section 12.4](../APP_NAVIGATION_AND_UX.md#124-streak-behavior) on 2026-09-08. `journeyStatistics` derives the approved streak alongside full/partial counts from known participation for every unlocked day. The pure Journey/day milestone is implemented; [testing evidence](testing.md#journey-domain-verification) records verification and its limits. The next critical-path dependency after deployed Data authorization verification is local persistence/synchronization; onboarding and feature screens must consume the focused service and this domain.

State is local React `useState` for control interactions and the native splash transition. Theme selection uses the system color scheme; all application consumers go through the shared hooks. The web color hook uses `useSyncExternalStore` with a light server/hydration snapshot and an `Appearance` subscription. A focused React Auth provider owns session state; the native service maps Amplify identity and errors to application types. Pending confirmation stores only email and version in one AsyncStorage record; Amplify owns its token persistence. No application Data cache, private-write queue, or general state framework exists. A focused curated Scripture data boundary now resolves published day/passages, available translations, stable preference IDs, and bundled text. The checked-in plan is an empty draft and all translations remain disabled; no production content or saved preference exists. V1 routes compose shared layouts, sections, state feedback, and navigation controls with static explanatory content. Data-dependent controls remain unconnected. A context scoped to the dynamic day layout contains only the validated route number; it is not journey or authentication state.

Amplify Gen 2 now defines the existing Cognito Lite email/password Auth plus a minimal private Data boundary. `UserProfile`, `Journey`, and `DailyEntry` each use owner authorization based on immutable Cognito `sub`; unsafe create/delete/list/subscription operations are disabled per model. One Node 24 Function derives the caller from AppSync identity and uses conditional DynamoDB writes for one-profile, one-V1-Journey, and Journey/day idempotency, relationship ownership, verified-email writes, day range, and immutable practice snapshots. It has only `GetItem`/`PutItem` access to those three model tables. There is no Community, journal, generic repository, or application Storage model. Amplify's generated Data machinery does synthesize internal schema/codegen S3 buckets and framework support Functions; these are not an app file-storage capability.

The native focused Data service maps generated records/errors to application-owned types and offers only profile, Journey, and DailyEntry operations needed by later features. Its web override remains an explicitly unsupported synthetic preview. It does not implement a durable local cache or pending-write queue. The backend is deployed to the isolated sandbox. Real synthetic two-user tests passed profile ownership, protected owner fields, Journey and DailyEntry cross-user reads/writes, generated-operation bypass attempts, protected DailyEntry history, indexed/list pagination isolation, unconfirmed/unauthenticated denial, cross-Journey ownership, concurrent/idempotent one-active-Journey enforcement, and Journey/day retry identity. This completes the Data authorization/invariant milestone without treating fixture content as an approved production curriculum.

The retained `auth-foundation` sandbox was previously deployed Auth-only in the owner-confirmed `us-east-1` development account. A synthetic admin-confirmed participant subsequently completed real SRP sign-in against its app client; the resulting Amplify session exposed a `userId` exactly equal to the immutable `sub`, and sign-out and immediate synthetic-user cleanup succeeded. This proves the sign-in/session identity seam used by Data, not self-service confirmation-code delivery, password recovery, native session restoration, or Data authorization. The generated outputs remain ignored and the environment is not production or preview.

`.gitignore` excludes `.env*` except `.env.example`, Amplify working artifacts/outputs, `.expo/`, `expo-env.d.ts`, native folders, coverage, lint cache, and `example/`.
